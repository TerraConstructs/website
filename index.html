Everything you need to know about TerraConstructs

TerraConstructs is a library of Level 2 CDKTF Constructs that are initially ported from AWS CDK L2 constructs. The key difference is that TerraConstructs synthesizes to pure Terraform/OpenTofu configurations instead of CloudFormation, allowing minimal effort adoption for teams with existing Terraform footprint while enabling the excellent developer experience AWS CDK is famous for.

CDKTF is a combination of a CLI, a core library and a collection of Level 1 Construct libraries auto generated from a select few terraform providers. This includes cloud providers such as AWS, but lacks any cloud specific functionality typically provided by L2 Constructs.

Example L2 Constructs functionality available in AWSCDK but missing in CDKTF: Service Common Usage Patterns, Asset pipelines, Permission management, Service Config DSLs, etc.

TerraConstructs is filling this gap by building the missing pieces available in AWS CDK on top of CDKTF.

TerraConstructs is initially a ported version of AWS CDK L2 constructs, but longer term aims to build L2 support for other cloud providers as well.

The terraform-provider-aws is the de-facto standard: broadest resource coverage, long production history, and first-class support across the TF ecosystem (tflint, Infracost, Checkov/OPA, Trivy SAST, etc.). awscc only reached GA in mid 2024 and still lags in coverage; its schemas and resource names differ, which breaks or dilutes many existing rules, cost mappings, and scanners.

The >AWS adapter (technical preview) maps final CloudFormation YAML into awscc resources. That loses important L2 synthesis logic and often can't represent the same graph: CFN sometimes nests multiple API concepts inside a single resource, while Terraform models them as separate resources with distinct lifecycles and dependencies. The result can be incomplete mappings, unstable plans, and missing features (such as the asset pipeline). TerraConstructs re-implements the AWS CDK L2 behaviors on top of provider-aws, preserving intent and producing Terraform resources that align with the provider and ecosystem tools.

TerraConstructs pairs perfectly with LLMs because its APIs are intent based. Clear class names, typed props, and enums give models the context they lack in raw HCL, while synth still produces deterministic, test-backed Terraform JSON.

Raw HCL is verbose and context heavy. LLMs tend to hallucinate enum values, miss nested attributes, and mis-wire dependencies. TerraConstructs collapse that surface area into typed, higher-level calls, so models (and humans) make fewer mistakes and ship faster. Moreover, a shared community effort for a well tested and deterministic library is more efficient than each team building their own prompt engineering and validation layers.
